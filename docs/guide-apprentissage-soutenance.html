2. Le projet ContainerLab en 5 minutes

ContainerLab est une implémentation académique d'excellence d'une application web multi-tiers (3-tiers) résiliente, conçue pour répondre à l'intégralité du cahier des charges de la Proposition 2 : Conteneurisation et Orchestration locale vs Cloud (Docker & Kubernetes / ECS).

Le projet matérialise le passage de la virtualisation lourde par hyperviseur (qui clone un OS invité complet avec son noyau) vers la conteneurisation légère (qui isole des processus partageant le même noyau Linux), à travers deux stades d'orchestration complémentaires :

  1. Stade 1 : Composition locale avec Docker Compose : segmentation réseau en zone démilitarisée (DMZ), synchronisation déterministe au démarrage via des sondes d'état saines (condition: service_healthy), et persistance des données sur volume nommé Docker.
  2. Stade 2 : Orchestration de Cluster avec Kubernetes sur Minikube : déploiement déclaratif de 10 manifestes ordonnés dans un Namespace isolé, provisionnement dynamique de stockage persistant (PVC 1Gi), découplage fin des sondes de vie et de préparation, équilibrage de charge via kube-proxy, redimensionnement dynamique de 2 à 4 réplicas, et auto-guérison autonome en cas de crash de conteneur.

3. Le pont complet avec le cours des professeures

Cette section est la clé de voûte de votre préparation : elle établit une passerelle directe et systématique entre les notions enseignées en cours magistral par Mme Imen Nasr et Mme Maymouna Ben Said et leur réalisation concrète dans ContainerLab.

3.1 Virtualisation Matérielle vs Conteneurisation OS

Cours Conteneurisation (slides 4 à 7) Cours Virtualisation (slides 4 à 7)

  • Ce que le cours enseigne : La virtualisation matérielle classique s'appuie sur un Hyperviseur (Type 1 bare-metal comme VMware ESXi/Hyper-V ou Type 2 hosted comme VirtualBox/VMware Workstation) pour émuler une machine physique complète. Chaque VM embarque son propre système d'exploitation invité (Guest OS), ce qui entraîne une consommation de stockage importante (plusieurs Go), une utilisation mémoire redondante et des temps de démarrage de plusieurs minutes. À l'inverse, la conteneurisation est une virtualisation au niveau du système d'exploitation qui ne virtualise pas le matériel mais crée des environnements isolés pour les processus en s'appuyant directement sur les fonctionnalités du noyau de l'hôte.
  • Ce que nous avons fait dans ContainerLab : Nous avons éliminé toute émulation matérielle. Nos conteneurs (Frontend, API, Database) s'exécutent directement sur le noyau Linux de l'hôte (via Docker Engine / WSL2). Leurs images pèsent entre 5.56 Mo et 110 Mo, démarrent en moins de 2 secondes, et partagent efficacement le CPU et la RAM de l'hôte sans couche d'hyperviseur intermédiaire.

3.2 Les Fondations du Noyau Linux : chroot, cgroups et namespaces

Cours Conteneurisation (slides 10 à 13) Cours Virtualisation (slides 30 à 33)

Le cours explique que la conteneurisation repose historiquement sur trois briques fondamentales du noyau Linux. Voici comment chacune d'elles opère concrètement dans notre projet :

Primitive Linux Définition & Rôle dans le Cours Mise en Œuvre dans ContainerLab
chroot (1979) Commande permettant de changer le répertoire racine (/) d'un processus et de ses sous-processus. Fournit un espace disque isolé ("chroot jail") mais n'offre aucune isolation de processus, de mémoire ou de réseau. Chaque conteneur de ContainerLab dispose de son propre système de fichiers racine (RootFS) étanche, empêchant un attaquant éventuel dans l'API d'accéder aux fichiers de l'hôte ou de la base.
cgroups (2006) Fonctionnalité du noyau Linux pour limiter, compter et isoler l'utilisation des ressources physiques : temps CPU, mémoire vive, bande passante réseau et entrées/sorties disque (I/O). Dans notre manifeste 06-api-deployment.yaml, nous déclarons des limites strictes :
resources.requests: { cpu: "100m", memory: "128Mi" }
resources.limits: { cpu: "250m", memory: "256Mi" }.
Le noyau Linux bride le CPU et déclenche l'OOM-Killer si la mémoire dépasse 256 MiB, protégeant le cluster du syndrome du "mauvais voisin".
namespaces (2008) Mécanisme qui partitionne les ressources globales du système pour donner à chaque groupe de processus sa propre vue unique et isolée :
  • pid : numérotation des processus
  • net : interfaces et tables de routage
  • mnt : points de montage de disques
  • ipc : mémoire partagée inter-processus
  • uts : nom d'hôte (hostname)
  • user : mappage des identifiants UID/GID
 Dans ContainerLab :
  • PID namespace : Le serveur Node.js voit son processus comme le PID 1 dans le conteneur API.
  • NET namespace : Chaque conteneur possède sa propre interface eth0 avec son adresse IP privée dédiée.
  • UTS namespace : Chaque réplica API possède son propre nom d'hôte généré par Kubernetes (ex: api-7d498b58f9-k2x89), affiché sur le dashboard.
  • USER namespace : L'API s'exécute sous le compte non-privilégié USER node (UID 1000) au lieu de root.

3.3 De LXC à Docker & la Philosophie "Un Conteneur = Un Service"

Cours Conteneurisation (slides 16 à 19)

  • Ce que le cours enseigne : LXC (2008) a intégré les cgroups et namespaces dans le noyau 2.6.24 pour créer des "conteneurs Linux". Cependant, LXC gère des conteneurs comme de petites machines virtuelles contenant de multiples processus et services. Docker (2013) a révolutionné l'industrie en apportant :
    1. La philosophie "un conteneur = un service" (une application multi-services se décompose en X conteneurs spécialisés).
    2. Le remplacement de LXC par libcontainer (puis runc) pour communiquer directement avec les APIs du noyau.
    3. L'automatisation de la construction via le fichier Dockerfile.
    4. La standardisation de la distribution via le concept d'Image et les dépôts (Docker Hub / Registries).
  • Ce que nous avons fait dans ContainerLab : Notre projet applique fidèlement la règle un conteneur = un service : nous avons créé 3 conteneurs distincts avec leurs propres Dockerfiles (Frontend Nginx, Backend Node.js, Base PostgreSQL), totalement découplés, faciles à maintenir, à mettre à l'échelle individuellement et à remplacer sans interrompre les autres briques.

3.4 Système de Fichiers Union (OverlayFS) et Multi-Stage Build

Cours Conteneurisation (slides 23, 26, 27)

  • Ce que le cours enseigne : Une image Docker est une succession de couches immuables (read-only layers) construites instruction par instruction dans le Dockerfile. Lorsqu'un conteneur démarre, Docker ajoute une fine couche inscriptible éphémère (writable layer) via le principe de Copy-on-Write (CoW). Pour optimiser la taille des images et la sécurité, il est crucial d'éliminer les outils de compilation de l'image finale.
  • Ce que nous avons fait dans ContainerLab : Dans application/frontend/Dockerfile, nous avons implémenté un Multi-Stage Build rigoureux :
    • Étape 1 (builder) : Utilise node:24-alpine pour télécharger les packages npm et compiler le code React/JSX avec Vite via npm run build.
    • Étape 2 (runner) : Utilise nginx:stable-alpine-slim. Nous copions uniquement le dossier compilé dist/ vers /usr/share/nginx/html et notre configuration nginx.conf.
🏆 Benchmark validé (Test T02) : Réduction de 93.1% de la taille d'image !
L'image non-optimisée embarquant le runtime Node.js et les outils de développement pesait 80.92 MB. L'image de production multi-stage ne pèse que 5.56 MB, soit un gain mesuré de -93.1% (-75.36 Mo d'économisés !).

3.5 Réseaux de Virtualisation vs Réseaux de Conteneurisation

Cours Virtualisation (slides 25 à 27) Cours Conteneurisation (slides 30 à 32)

Le cours de virtualisation détaille les trois modes d'accès réseau pour les machines virtuelles, et le cours de conteneurisation présente les pilotes Docker. Voici la comparaison directe :

Mode Réseau (Cours) Principe & Fonctionnement Équivalent Concret dans ContainerLab
Network Bridging (Pont) La VM dispose d'un accès direct au réseau physique indépendamment du système hôte, avec sa propre adresse IP sur le LAN. Dans Docker, le pilote bridge crée un commutateur virtuel logiciel (ex: docker0) isolant les conteneurs sur un sous-réseau privé. Sous Docker Compose, nous avons créé deux réseaux ponts : frontend-net et backend-net. Les conteneurs communiquent par DNS interne (ex: http://api:5000).
NAT (Network Address Translation) La VM est sur un réseau virtuel privé masqué derrière l'adresse IP de l'hôte. L'hyperviseur effectue une translation d'adresses et de ports (Port Forwarding / Port Publishing -p). Le mapping ports: ["3000:80"] dans Compose et nodePort: 30080 dans Kubernetes acheminent le trafic de l'hôte vers le port interne du conteneur Nginx.
Host-Only Networking Réseau totalement privé et isolé permettant uniquement la communication entre les VMs et l'hôte, sans aucun accès au monde extérieur. Le réseau backend-net de Compose isole la base PostgreSQL. Elle n'expose aucun port sur l'hôte et n'est accessible que par le conteneur API.
Kubernetes Services (ClusterIP & NodePort) Abstractions Kubernetes gérant l'équilibrage de charge et la découverte de services via des adresses IP virtuelles stables et des règles iptables pilotées par kube-proxy. service/api et service/postgres utilisent ClusterIP (VIP interne). service/frontend utilise NodePort (port statique 30080).

3.6 Stockage et Persistance des Données

Cours Conteneurisation (slide 34)

  • Ce que le cours enseigne : Les conteneurs sont intrinsèquement éphémères : les fichiers modifiés dans la couche inscriptible sont perdus lors de la destruction du conteneur. Le cours présente 3 mécanismes de stockage :
    1. tmpfs mount : stockage volatile en mémoire RAM de l'hôte.
    2. bind mount : montage direct d'un dossier du système de fichiers hôte dans le conteneur.
    3. volume Docker : stockage persistant géré par le moteur Docker, isolé du système de fichiers hôte.
  • Ce que nous avons fait dans ContainerLab :
    • Sous Docker Compose : Utilisation d'un volume nommé postgres_data monté sur /var/lib/postgresql/data. Les annonces saisies résistent à la commande docker compose restart postgres.
    • Sous Kubernetes : Déclaration d'un PersistentVolumeClaim (PVC) de 1Gi (03-database-pvc.yaml) provisionné dynamiquement par la standard StorageClass de Minikube. Même si le Pod PostgreSQL est supprimé par kubectl delete pod, le contrôleur recrée un Pod qui s'accroche au même volume persistant, conservant 100% des données (validé par le test T10).

3.7 Modèles de Service Cloud : IaaS, PaaS, SaaS, NaaS, IDaaS, SSO

Cours Cloud Computing (slides 15, 16, 50 à 70)

Le cours de Mme Nasr définit les modèles de service de référence ("XaaS - Anything as a Service") ainsi que le partage de responsabilités. Voici comment ContainerLab s'inscrit dans cette taxonomie :

Modèle Cloud Définition du Cours Positionnement vis-à-vis de ContainerLab
IaaS (Infrastructure as a Service) Fournit des ressources fondamentales : machines virtuelles (ex: AWS EC2), stockage en bloc/objet (EBS, S3), et réseau virtuel (VPC). Le client gère l'OS, les runtimes et les applications. Nos conteneurs peuvent tourner sur des instances virtuelles IaaS EC2 provisionnées manuellement ou gérées dans un cluster Minikube local.
PaaS (Platform as a Service) Fournit l'environnement d'exécution, les bibliothèques et les outils de déploiement (ex: AWS Elastic Beanstalk, Heroku). L'utilisateur n'administre pas le serveur ni l'OS. Kubernetes fonctionne comme un métamodèle PaaS : il abstrait les machines physiques pour offrir une plateforme d'exécution déclarative.
SaaS (Software as a Service) L'application logicielle complète est délivrée clé en main via un navigateur web (ex: Gmail, Salesforce, Google Docs). Tout est géré par le fournisseur. Du point de vue des utilisateurs finaux qui consultent et postent des annonces dans le navigateur, ContainerLab fonctionne comme un service SaaS.
NaaS (Network as a Service) Virtualisation de l'infrastructure réseau (SDN), déploiement de protocoles de routage personnalisés et connectivité sécurisée à la demande. Illustré par notre segmentation en sous-réseaux isolés, répliquée sur AWS via Amazon VPC.
IDaaS & SSO (Single Sign-On) Gestion centralisée des identités et authentification unique basée sur des serveurs de tickets pour éviter les multiples identifiants (cours p. 66-68). Dans une extension de production, ContainerLab déléguerait l'authentification à un fournisseur IDaaS (ex: AWS Cognito, Keycloak, Auth0) avec jetons JWT signés.

3.8 Modèles de Déploiement Cloud

Cours Cloud Computing (slides 14, 29 à 39)

  • Cloud Public : Infrastructure mutualisée accessible à grande échelle via Internet (AWS, Azure, GCP). Offre une très haute élasticité mais une sécurité partagée. C'est la cible de déploiement cloud de ContainerLab via AWS EKS ou ECS.
  • Cloud Privé : Infrastructure dédiée à une seule organisation. Sécurité et contrôle maximaux, mais coûts d'acquisition de matériel élevés et passage à l'échelle limité. C'est l'équivalent de notre cluster local Minikube sur machine dédiée.
  • Cloud Hybride : Combinaison de cloud privé (pour les données critiques, comme notre base PostgreSQL) et de cloud public (pour absorber les pics de charge sur l'API ou le frontend web).
  • Cloud Communautaire : Infrastructure mutualisée entre plusieurs organisations partageant des exigences communes (ex: plateforme inter-universitaire tunisienne pour les établissements de l'enseignement supérieur).

3.9 L'Étude de Cas Wikileaks & Les Leçons de Résilience Cloud

Cours Cloud Computing (slides 40 à 47)

  • Rappel de l'affaire étudiée en cours : En novembre 2010 ("Cablegate"), Wikileaks publie des milliers de câbles diplomatiques sensibles. Le site subit des attaques DDoS massives (>10 Gbps) rendant ses serveurs indisponibles. Wikileaks migre en urgence sur le Cloud Amazon AWS (EC2/S3), qui absorbe l'attaque grâce à son réseau élastique. Cependant, sous pression politique, Amazon rompt unilatéralement son contrat, et le registrar DNS supprime le nom de domaine wikileaks.org. Wikileaks a dû se rabattre sur des miroirs P2P et des hébergeurs souverains (OVH en France).
  • Ce que ce cas démontre pour notre projet :
    1. La force du Cloud et des Conteneurs : La portabilité des conteneurs permet de migrer une application d'un fournisseur à un autre (ou du local vers le cloud) en quelques secondes, sans réécrire le code.
    2. La protection contre le Lock-In : En utilisant des manifestes Kubernetes déclaratifs standards plutôt que des services propriétaires fermés, nous évitons la dépendance captive ("Vendor Lock-in") mise en lumière par l'éviction brutale d'Amazon en 2010.
    3. L'absorption des hausses de trafic : Grâce à la commande kubectl scale et à l'équilibrage de charge, ContainerLab est conçu pour absorber les augmentations soudaines de requêtes sans tomber en panne.

3.10 Gestionnaire de Machines Virtuelles (Sandpiper) vs Kubernetes Control Plane

Cours Virtualisation (slides 34 à 37) Cours Conteneurisation (slides 42 à 46)

Critère Gestionnaire de VM classique (Sandpiper - 2009) Orchestrateur de Conteneurs Moderne (Kubernetes)
Unité d'Orchestration Machine Virtuelle complète (OS invité + kernel + disques virtuels de plusieurs Go). Pod : plus petite unité orchestrable, regroupant un ou plusieurs conteneurs légers partageant le même namespace réseau.
Détection de Surcharge Surveille les "hotspots" (nœuds physiques où l'utilisation CPU, RAM ou disque franchit des seuils de saturation). Kubelet et Metrics Server surveillent en continu la consommation des Pods par rapport aux requests et limits des cgroups.
Résolution du Problème Live Migration de la VM vers une autre machine physique moins chargée, via des techniques de Pre-Copy (copie itérative des dirty pages en mémoire) ou Post-Copy (temps de migration réduit mais risque d'état distribué). Autoscaling Horizontal (HPA) : Au lieu de déplacer une VM géante, Kubernetes clone instantanément de nouveaux Pods réplicas sur les nœuds disponibles, et kube-proxy répartit la charge. En cas de panne d'un nœud, le Scheduler replanifie simplement le Pod ailleurs.

4.3 Le Trajet d'une Requête de Bout en Bout (Exemple : Créer une Annonce)

  1. Action utilisateur : Sur le dashboard React, l'utilisateur remplit le formulaire et clique sur "Publier l'annonce". La fonction fetch('/api/announcements', { method: 'POST', body: ... }) est déclenchée.
  2. Arrivée sur le port externe : La requête HTTP arrive sur le port publié de l'hôte (3000 en Compose, ou 30080 en Minikube).
  3. Routage Nginx (Tier 1) : Le serveur web Nginx reçoit la requête. La directive location /api/ de nginx.conf intercepte l'appel et effectue un reverse proxy transparent vers le nom d'hôte interne : 
    location /api/ {
    proxy_pass http://api:5000/api/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
}
  4. Traitement API Express (Tier 2) : Le serveur Node.js reçoit la requête sur le port 5000 :
    • Le middleware de journalisation note la requête avec le nom d'hôte du pod (os.hostname()).
    • Le contrôleur valide que les champs title et content ne sont pas vides, supprime les espaces superflus (trim()), et vérifie les plafonds (150 caractères pour le titre, 2000 pour le contenu).
    // Extrait de application/backend/src/app.js
const result = await db.query(
  'INSERT INTO announcements (title, content, author) VALUES ($1, $2, $3) RETURNING *;',
  [title, content, author]
);
res.status(201).json({ success: true, podName: os.hostname(), data: result.rows[0] });
  5. Persistance PostgreSQL (Tier 3) : Le client PostgreSQL (pg.Pool) envoie la requête paramétrée sur le port 5432. PostgreSQL écrit la ligne dans la table announcements, dont les données résident physiquement sur le volume persistant.
  6. Retour de la réponse : L'API répond avec le code HTTP 201 Created et le nom du Pod ayant traité l'opération. Nginx retransmet le JSON au navigateur. Le composant React met à jour le fil d'annonces instantanément sans recharger la page.

4.4 Le Grand Secret d'Architecture : Pourquoi Nginx en Reverse Proxy ?

⚠️ Question Piège n°1 des Professeures à la Soutenance !
"Pourquoi ne pas appeler directement http://api:5000 depuis votre code React dans le navigateur ?"

Voici l'explication technique que le jury attend :

Une application React (Single Page Application) est compilée en amont en fichiers HTML et JavaScript statiques. Ce code JavaScript ne s'exécute PAS dans un conteneur sur le serveur, mais directement dans le moteur JavaScript du navigateur web de l'utilisateur, sur la machine hôte Windows.

Or, le système d'exploitation de la machine hôte est totalement incapable de résoudre les noms d'hôtes internes du réseau Docker ou du cluster Kubernetes (comme http://api:5000 ou http://postgres:5432), car ces noms sont résolus par le serveur DNS interne de Docker (127.0.0.11) ou CoreDNS dans Kubernetes, accessibles uniquement depuis l'intérieur des conteneurs.

Si le code React appelait http://api:5000, la requête échouerait immédiatement avec l'erreur ERR_NAME_NOT_RESOLVED.

En plaçant Nginx en reverse proxy dans le conteneur frontend :

  • Résolution de même origine (Same-Origin) : Le navigateur envoie toutes ses requêtes sur la même adresse et le même port que le site web (/api/*). Zéro problème de CORS (Cross-Origin Resource Sharing) !
  • Sécurité maximale : Un seul port public est ouvert sur l'hôte (port 3000 ou 30080). Les ports de l'API (5000) et de PostgreSQL (5432) restent 100% privés et inaccessibles depuis l'extérieur.
  • Portabilité absolue : La configuration fonctionne à l'identique sous Docker Compose et sous Kubernetes sans changer une seule ligne de code côté frontend.

4.5 L'Isolation DMZ sous Docker Compose

Dans compose.yaml, nous avons rejeté le réseau par défaut unique pour configurer deux réseaux bridge segmentés :

# compose.yaml (extrait de segmentation)
services:
  frontend:
    networks:
      - frontend-net    # Accède à l'API uniquement
  api:
    networks:
      - frontend-net    # Rejoint le frontend
      - backend-net     # Rejoint la base de données
  postgres:
    networks:
      - backend-net     # Isolé ! Inaccessible depuis frontend-net

networks:
  frontend-net:
    driver: bridge
  backend-net:
    driver: bridge

Preuve formelle d'isolation : Si un assaillant compromettait le serveur Nginx dans le conteneur frontend et tentait de contacter directement PostgreSQL :

docker exec containerlab-frontend ping postgres
# Résultat : Ping request could not find host postgres. Isolation validée !

4.6 Sécurité des Conteneurs : Utilisateur Non-Root & Secrets Découplés

  • Exécution non-root (USER node) : Par défaut, un conteneur Docker s'exécute avec les privilèges root. Si une faille d'exécution de code à distance (RCE) survient dans l'API, l'attaquant possède les droits root dans le conteneur et peut tenter une évasion de noyau. Dans application/backend/Dockerfile, nous forçons l'instruction USER node (UID standard 1000). Le processus Node.js s'exécute sans aucun droit d'administration système.
  • Découplage Configuration / Secrets : Aucune chaîne de connexion ni mot de passe n'est écrit en dur dans le code source. Les variables de configuration non sensibles (noms de tables, ports) sont injectées par le ConfigMap (01-configmap.yaml), et les identifiants d'accès PostgreSQL sont injectés via un Secret Kubernetes (02-api-secret.yaml).

6. Les 8 règles d'or d'ingénierie à connaître par cœur

Ces huit règles sont les choix techniques majeurs qui font la solidité professionnelle de ContainerLab. Si vous savez les énoncer et expliquer leur raison d'être, vous démontrez une maturité d'ingénieur remarquable :

Règle 1 : Multi-Stage Build obligatoire pour les applications compilées
Pourquoi : Dans une application React ou Angular, les compilateurs (Node.js, Vite, npm) ne servent qu'au moment de la fabrication (build). Les inclure dans l'image finale augmente la surface d'attaque et multiplie le poids de l'image par 15. En ne copiant que le dossier dist/ dans nginx:stable-alpine-slim, l'image passe de 80.92 MB à 5.56 MB (-93.1%).
Règle 2 : Stratégie 'Recreate' impérative pour les bases de données sur volume ReadWriteOnce
Pourquoi : Par défaut, un Déploiement Kubernetes utilise la stratégie RollingUpdate (il démarre le nouveau Pod avant de tuer l'ancien pour assurer le zéro downtime). Mais un volume persistant EBS ou HostPath est de type ReadWriteOnce (un seul nœud/pod peut monter le disque en écriture à la fois). Si Kubernetes lance le nouveau Pod DB alors que l'ancien n'est pas encore éteint, le montage échoue avec l'erreur bloquante Multi-Attach error for volume. Définir strategy: { type: Recreate } dans 04-database-deployment.yaml force Kubernetes à éteindre l'ancien Pod avant de monter le disque sur le nouveau.
Règle 3 : Découpler strictement la sonde de vie (Liveness) et la sonde de préparation (Readiness)
Pourquoi : La sonde de vivacité (/api/health/live) teste uniquement si le processus Node.js tourne. La sonde de préparation (/api/health/ready) teste si la connexion à PostgreSQL est active. Si l'on mettait le test de base de données dans la sonde de vivacité, un simple redémarrage temporaire de PostgreSQL entraînerait l'échec de la sonde de vie de l'API : Kubernetes tuerait alors tous les Pods API en boucle, provoquant un redémarrage en cascade catastrophique ! Avec notre découplage, si la base redémarre, l'API échoue seulement à sa Readiness probe : Kubernetes retire temporairement le Pod de l'équilibreur sans le tuer, jusqu'au retour de la base.
Règle 4 : 'imagePullPolicy: Never' et versionnement sémantique strict en local
Pourquoi : Si une image utilise le tag latest, Kubernetes applique par défaut la politique imagePullPolicy: Always et cherche à télécharger l'image sur Docker Hub. Sur une machine locale ou sans connexion Internet, le déploiement échoue avec ErrImagePull. En utilisant des tags précis (v1.0.0) et la directive imagePullPolicy: Never, nous garantissons une évaluation 100% hors-ligne et reproductible depuis le cache Minikube.
Règle 5 : Exécution sous utilisateur non-root ('USER node')
Pourquoi : Le noyau Linux partage ses tables d'UID entre l'hôte et les conteneurs. Exécuter un conteneur en root expose la machine hôte à des attaques d'élévation de privilèges en cas de faille applicative. L'instruction USER node dans application/backend/Dockerfile confine l'application dans un compte sans droit sudo.
Règle 6 : Un Namespace Kubernetes est une frontière administrative, pas un pare-feu réseau
Pourquoi : Beaucoup de candidats commettent l'erreur de croire qu'isoler des Pods dans le Namespace containerlab empêche les autres Pods du cluster de leur parler. C'est faux : par défaut, le réseau Kubernetes est plat (flat network). L'isolation réseau stricte exige des ressources NetworkPolicy associées à un CNI compatible (Calico, Cilium). Dans notre projet, l'isolation réseau physique est démontrée sous Docker Compose via les réseaux bridge étanches.
Règle 7 : Synchronisation déterministe au démarrage ('condition: service_healthy')
Pourquoi : Par défaut, Docker Compose lance les conteneurs en parallèle. Un conteneur PostgreSQL met plusieurs secondes à initialiser ses fichiers de données et exécuter init.sql. Si l'API démarre en même temps, elle tente de se connecter à un port 5432 fermé et crashe. La clause depends_on: { postgres: { condition: service_healthy } } oblige l'API à attendre le code retour succès de pg_isready.
Règle 8 : Service NodePort 30080 pour l'évaluation autonome
Pourquoi : Sur un cluster de production AWS, l'accès externe se fait via un Ingress Controller relié à un Application Load Balancer (ALB). En environnement local Minikube sur Windows, le contrôleur Ingress nécessite l'activation de tunnels ou de modules complémentaires souvent instables. Utiliser un service NodePort sur le port fixe 30080 assure une démonstration infaillible, sans dépendance externe.

9. Questions probables à la soutenance (18 Questions & Réponses percutantes)

Voici les questions techniques les plus fréquemment posées par les jurys lors des soutenances de projets de virtualisation et cloud. Apprenez à formuler ces réponses avec vos propres mots :

Q1 : Quelle est la différence fondamentale entre une Machine Virtuelle et un Conteneur Docker ?

Une Machine Virtuelle virtualise le matériel via un Hyperviseur (Type 1 ou Type 2). Chaque VM charge un système d'exploitation invité complet avec son propre noyau (kernel), ce qui consomme plusieurs gigaoctets et demande des minutes pour démarrer.

Un Conteneur effectue une virtualisation au niveau du système d'exploitation : il partage directement le noyau Linux de la machine hôte. Il isole les processus grâce aux Namespaces (qui limitent ce que le processus peut voir) et aux cgroups (qui limitent ce que le processus peut utiliser). Un conteneur démarre en quelques millisecondes et ne pèse que quelques mégaoctets.

📁 Référence : Diapositives Conteneurisation (p. 4-6) & Virtualisation (p. 5-7).
Q2 : Pourquoi avoir utilisé un Reverse Proxy Nginx plutôt que d'exposer directement le port de l'API Node.js ?

Notre interface React s'exécute côté client dans le navigateur de l'utilisateur sur la machine hôte. L'hôte Windows ne peut pas résoudre les noms d'hôtes internes du réseau de conteneurs (http://api:5000). Nginx sert le site web et relaie en interne les requêtes /api/* vers le conteneur API. Cela garantit une communication Same-Origin (zéro erreur CORS) et permet de n'exposer qu'un seul port public (3000 ou 30080), laissant l'API et la base totalement privées.

📁 Référence : application/frontend/nginx.conf & ADR-001.
Q3 : Pourquoi avoir choisi un Déploiement avec PVC plutôt qu'un StatefulSet pour PostgreSQL ?

Dans notre projet, PostgreSQL est une instance unique autonome sans réplication ni cluster maître-esclave. Le StatefulSet est indispensable lorsqu'on gère des identités réseau ordinales et ordonnées (postgres-0, postgres-1). Pour une instance unique, un Deployment avec 1 réplica, un PVC et la stratégie Recreate offre la persistance requise tout en garantissant que l'ancien Pod libère le verrouillage du volume ReadWriteOnce avant que le nouveau ne le monte.

📁 Référence : kubernetes/04-database-deployment.yaml & ADR-002.
Q4 : Pourquoi découpler la sonde de vivacité (Liveness) de la sonde de préparation (Readiness) ?

La sonde Liveness (/api/health/live) surveille la santé du processus Node.js. Si elle échoue, Kubernetes redémarre le conteneur. La sonde Readiness (/api/health/ready) vérifie que la connexion PostgreSQL est active. Si la base de données est temporairement redémarrée, la Readiness échoue et Kubernetes retire le Pod du pool de routage sans le tuer. Si nous avions testé la base dans la Liveness, Kubernetes aurait tué et redémarré en boucle tous les Pods API, créant une tempête de reboots en cascade.

📁 Référence : application/backend/src/app.js (lignes 22-58) & kubernetes/06-api-deployment.yaml.
Q5 : Pourquoi configurer 'imagePullPolicy: Never' dans vos manifestes Kubernetes ?

En utilisant le tag latest, Kubernetes applique par défaut la politique Always et tente de télécharger l'image depuis Docker Hub, ce qui provoque une erreur ImagePullBackOff si les images ne sont pas publiées publiquement. En taguant nos images en v1.0.0 et en définissant imagePullPolicy: Never, nous forçons Kubernetes à utiliser les images préchargées dans le cache de Minikube (via minikube image load), assurant une reproductibilité parfaite et autonome sans connexion Internet.

📁 Référence : kubernetes/06-api-deployment.yaml & ADR-003.
Q6 : Comment la segmentation réseau de Docker Compose protège-t-elle votre base de données ?

Dans compose.yaml, nous déclarons deux réseaux ponts : frontend-net et backend-net. Le conteneur frontend appartient uniquement à frontend-net, postgres uniquement à backend-net, et l'API api rejoint les deux. Parce que les ponts Docker isolent le trafic ARP et IP de niveau 2 et 3, le conteneur Nginx est techniquement incapable de joindre ou de pinger le port 5432 de la base de données.

📁 Référence : compose.yaml (lignes 81-90) & ADR-004.
Q7 : Un Namespace Kubernetes fournit-il une isolation de sécurité réseau par défaut ?

Non. Un Namespace Kubernetes est une frontière administrative et logique (il permet d'attribuer des quotas de ressources et d'éviter les collisions de noms entre équipes). Par défaut, le réseau Kubernetes est totalement plat : n'importe quel Pod d'un autre namespace peut envoyer des paquets IP à nos Pods. Pour obtenir une véritable isolation réseau dans Kubernetes, il faut déclarer des ressources NetworkPolicy avec un plugin CNI compatible (comme Calico ou Cilium).

📁 Référence : Diapositives Conteneurisation (p. 44) & README.md.
Q8 : Comment avez-vous obtenu une réduction de 93.1% sur la taille de l'image Frontend ?

Grâce au Multi-Stage Build. Dans une image standard à un seul étage, l'image finale embarque le runtime Node.js, le gestionnaire npm, les modules node_modules et le code source (80.92 MB). Notre Dockerfile sépare la construction en deux étages : l'étape builder compile les sources en HTML/CSS/JS pur dans le dossier dist/, puis l'étape runner copie uniquement ce dossier dans nginx:stable-alpine-slim. Tout l'outillage de compilation est jeté, produisant une image finale de seulement 5.56 MB.

📁 Référence : application/frontend/Dockerfile & docs/benchmarks/image-sizes.md.
Q9 : Que se passe-t-il si un Pod API plante ou est supprimé brutalement en production ?

Le contrôleur ReplicaSet de Kubernetes applique la boucle de réconciliation continue : il compare l'état désiré (déclaré dans le Deployment, ex: 2 réplicas) avec l'état réel du cluster. Dès que le Pod disparaît, le ReplicaSet instancie immédiatement un Pod de remplacement, le Scheduler l'affecte à un nœud disponible, et le Kubelet démarre le conteneur. Dès que la sonde Readiness est validée, le Pod est réintégré au Service. Le client ne subit aucune interruption de service.

📁 Référence : kubernetes/06-api-deployment.yaml & Test T09.
Q10 : Comment vos données PostgreSQL survivent-elles à la destruction de son Pod ?

Le Pod monte un PersistentVolumeClaim (03-database-pvc.yaml) de 1Gi. Ce PVC est lié à un volume persistant physique managé par la StorageClass de Minikube. Lorsque le Pod PostgreSQL est détruit, le cycle de vie du volume persistant reste indépendant du Pod. Le nouveau Pod instancié par le Deployment ré-attache le même volume et retrouve immédiatement les tables et les données existantes.

📁 Référence : kubernetes/03-database-pvc.yaml & Test T10.
Q11 : Comment se fait la découverte de service (Service Discovery) dans Kubernetes ?

Dans Kubernetes, les Pods ont des adresses IP dynamiques qui changent à chaque recréation. Pour les stabiliser, on associe aux Pods un Service (ex: service/api). Kubernetes lui attribue une adresse IP virtuelle fixe (ClusterIP) et enregistre son nom dans le serveur DNS interne du cluster (CoreDNS). Les autres conteneurs peuvent alors simplement contacter http://api:5000. Le composant kube-proxy intercepte ces requêtes et les redirige vers les adresses IP réelles des Pods sains.

📁 Référence : kubernetes/07-api-service.yaml & Diapositives Conteneurisation (p. 45).
Q12 : Quelle est la différence entre un Service ClusterIP et un Service NodePort ?

Un Service ClusterIP est le type par défaut : il n'est accessible que depuis l'intérieur du cluster via une adresse IP virtuelle privée (utilisé pour notre API et notre base). Un Service NodePort ouvre un port statique dédié (compris entre 30000 et 32767) sur toutes les interfaces réseau de chaque nœud du cluster, permettant à des clients externes d'accéder au service (utilisé sur le port 30080 pour notre Frontend).

📁 Référence : kubernetes/05-database-service.yaml & kubernetes/09-frontend-service.yaml.
Q13 : Comment fonctionne le contrôle des ressources via les cgroups dans vos manifestes ?

Dans 06-api-deployment.yaml, nous déclarons requests (ressources garanties réservées par le Scheduler pour placer le Pod) et limits (plafond maximal autorisé). Pour la mémoire (256Mi), si le conteneur dépasse la limite, le noyau Linux déclenche l'Out-Of-Memory Killer (OOM-Kill) et redémarre le conteneur. Pour le CPU (250m = 0.25 cœur), le noyau Linux utilise le Completely Fair Scheduler (CFS) pour brider les cycles processeur sans tuer le processus.

📁 Référence : Diapositives Conteneurisation (p. 11) & kubernetes/06-api-deployment.yaml.
Q14 : Pourquoi exécuter l'API Node.js avec 'USER node' plutôt qu'en utilisateur par défaut ?

Par défaut, Docker exécute les conteneurs avec l'UID 0 (root). Si une faille dans une dépendance npm permet à un attaquant d'exécuter des commandes à distance, il dispose des privilèges administrateur à l'intérieur du conteneur et peut exploiter une vulnérabilité du noyau pour s'échapper sur l'hôte. Avec USER node, le processus tourne avec un compte applicatif restreint, respectant le principe du moindre privilège.

📁 Référence : application/backend/Dockerfile (ligne 22).
Q15 : Comment les secrets sont-ils gérés entre votre démo et un environnement de production ?

Dans notre projet académique, nous découplons la configuration dans un ConfigMap et les identifiants dans un Secret natif (02-api-secret.yaml). Cependant, les Secrets natifs de Kubernetes ne sont que de simples chaînes encodées en Base64. En production sur AWS, nous utiliserions AWS Secrets Manager avec chiffrement d'enveloppe via AWS KMS, synchronisé dans le cluster via l'External Secrets Operator (ESO) avec rotation automatique des mots de passe.

📁 Référence : kubernetes/02-api-secret.yaml & docs/aws-comparison.md.
Q16 : En quoi l'étude de cas Wikileaks du cours de Cloud s'applique-t-elle à ContainerLab ?

En 2010, Wikileaks a subi une attaque DDoS géante (>10 Gbps) puis une rupture brutale de contrat par Amazon AWS. Cela nous apprend que la résilience repose sur deux piliers : l'élasticité (pouvoir multiplier les réplicas face à une charge soudaine, comme nous le faisons avec kubectl scale) et la portabilité sans vendor lock-in (nos conteneurs peuvent être redéployés à l'identique sur n'importe quel cloud ou sur site en une commande).

📁 Référence : Diapositives Cloud Computing (p. 40-47).
Q17 : Comment votre projet serait-il déployé sur AWS en environnement de production ?

Sur AWS :

  • Le cluster Minikube deviendrait un cluster managé Amazon EKS avec nœuds managés multi-AZ.
  • Le service NodePort serait remplacé par un Application Load Balancer (ALB) avec certificat SSL et protection AWS WAF.
  • Les images locales seraient stockées sur Amazon ECR avec scan de vulnérabilités CVE.
  • La base de données PostgreSQL conteneurisée serait remplacée par une instance managée Amazon RDS PostgreSQL Multi-AZ avec basculement automatique et sauvegardes continues.
📁 Référence : docs/aws-comparison.md.
Q18 : Quel est l'équivalent de votre architecture sous Amazon ECS et AWS Fargate ?

Dans Amazon ECS, le Pod Kubernetes correspond à une Task Definition (qui déclare les images de conteneurs, le CPU et la RAM). Le Deployment Kubernetes correspond à un ECS Service (qui maintient le nombre de tâches désiré). En mode AWS Fargate, nous n'avons aucune machine virtuelle EC2 à gérer : AWS gère le serveur et le noyau, et facture uniquement le CPU et la mémoire consommés par tâche à la seconde.

📁 Référence : README.md (Section 11) & docs/aws-comparison.md (Section 5).
